# Lion City Rails

A Ticket to Ride-style train game on a map of Singapore, for 2 to 5 players, each on their own device.
Claim MRT routes, connect your destination tickets and build the longest line. Bugis is the busiest interchange.

The whole game is one static page (`index.html`), so any static host can serve it. There is no game server:
the host's browser runs the game and friends connect straight to it.

## Put it online with GitHub Pages

1. Create a new **public** repository on github.com (for example `lion-city-rails`). Leave it empty.
2. In this folder, run:

   ```bash
   git init
   git add .
   git commit -m "Lion City Rails"
   git branch -M main
   git remote add origin https://github.com/<your-username>/lion-city-rails.git
   git push -u origin main
   ```

3. On GitHub open **Settings → Pages**. Under "Build and deployment" choose **Deploy from a branch**, branch `main`, folder `/ (root)`, and save.
4. After a minute or two the game is live at `https://<your-username>.github.io/lion-city-rails/`.

## How to play online

1. One person opens the page, types a name and presses **Host a game**.
2. They send friends the **invite link** (or the 4-letter code) from the lobby.
3. Friends open the link, type a name and press **Join**.
4. The host picks how many computer players to add (0 to 4) and presses **Start game**.

The rules are under **How to play** in the game.

## How the multiplayer works

* [PeerJS](https://peerjs.com) (WebRTC) connects the browsers. Its free public broker only introduces them to each other; the game data then goes directly between devices.
* The **host's browser is the game server**. Keep the host's tab open while you play. If the host reloads the page, press **Rejoin game** and the game resumes where it was; friends reconnect on their own.
* The host also plays the computer players.
* Friends can reload or close their tab and come back with the same code to keep their seat. Anyone who joins after the game has started watches as a spectator.
* The invite link is just the page address with `?join=CODE` on the end.

### Good to know

* The public PeerJS broker is free and has no uptime guarantee. If it is ever down, the page says it could not reach the connection service. You can run your own with `npm i peer` and `node test/broker.js 9000`, then open the page with `?broker=your-host:9000` (add `&secure=1` if it is served over HTTPS).
* PeerJS uses a Google STUN server and PeerJS's own TURN relays to get through home routers and most mobile networks. A few strict school or office networks block peer-to-peer traffic; the game will not connect on those.
* Like any WebRTC game, players' devices can see each other's network addresses while connected.
* Nothing is stored on a server. The host's browser keeps a copy of the current game in its local storage so a reload can resume it.

## Developing

```bash
python3 build.py        # writes index.html from src/
python3 -m http.server  # then open http://localhost:8000
node test/sim.js        # thousands of computer-vs-computer games: rules, scoring, balance
```

Browser test of a full multiplayer game (needs `pip install playwright`, `playwright install chromium` and `npm install`):

```bash
node test/broker.js 9000 &    # local PeerJS broker
python3 test/p2p_test.py
```

The map (stations, routes, tickets and the painted coastline) is generated by `mapgen.py` into `src/mapdata.js`
(needs `pip install shapely`). The real coastline comes from `geo/coast.json`; `geo/extract.py` shows how it was extracted.

| File | What it is |
| --- | --- |
| `src/engine.js` | Game rules: setup, turns, claiming, scoring, game end |
| `src/ai.js` | Computer players |
| `src/net_p2p.js` | The peer-to-peer online layer (host, join, reconnect, spectators) |
| `src/map.js`, `src/scenery.js` | The SVG board, painted terrain and landmark illustrations |
| `src/ui.js`, `src/style.css`, `src/template.html` | Interface |
| `src/mapdata.js` | Generated map data (do not edit by hand) |
